# Folduct 웹 구현 진행 기록

문서 생성일 2026년 10월 4일. 이 문서의 최초 상태는 **모든 구현 단계 시작 전**이다. 기존 파일 탐색 프로토타입이 있다는 사실을 새 PRD의 구현 완료로 간주하지 않는다.

## 현재 상태

- 현재 단계: 5단계 중단·장면·재개 구현 후 검증 진행 중
- 마지막 완료 단계: 4단계 미리보기와 보기 상태
- 다음 행동: 5단계의 실제 폴더·브라우저 재실행 검증을 마친 뒤 6단계 권한 재연결과 파일 변경으로 진행. Kook·모바일 가방·동기화는 별도 범위
- 기준 문서: `docs/folduct-prd-v2.0.md` (1.0의 FR01~14는 2.0 6장 변경점 외 유효)
- 방 돌보기: 2026-10-18 C1~C6과 ‘차 한 잔’ 시각 언어 구현. 아래 ‘방 돌보기 기록’ 참고
- 빌드 상태: 2026-10-06 `apps/web` 작업 복사본에서 TypeScript와 Vite 프로덕션 빌드 성공
- 테스트 상태: `vitest run` 46개 통과. Node와 fake-indexeddb이며 브라우저 저장소를 대체하지 않음
- 실제 브라우저 검증: Cursor 내장 브라우저에서 샘플 카드의 텍스트·SVG·HTML·PNG·음원·한글 파일 미리보기와 재생 위치 복원을 확인. 실제 폴더 선택과 영상 파일은 여전히 미검증
- 화면 맞춤: 책상 1440×900은 남은 화면 안에 비율을 유지한 채 들어간다. 1280px 이상은 세 칸, 1024~1279px는 자료·메모를 겹쳐 열고, 1024px 미만은 작업면·자료·메모 탭이다. 화면 크기는 저장된 카드 좌표를 바꾸지 않는다

## 2026-10-06 보강 기록 — 중단·재개와 선택형 시각화

5단계 기능을 구현했다. ‘여기서 멈추기’와 수동 장면 저장, 장면 목록과 읽기 전용 배치 미리보기, 과거 장면 이어가기 시 안전 장면 보존, 재방문 시 마지막 선택·이유·다음 행동을 모은 재개 요약을 제공한다. 작업면·장면·마지막 중단 참조와 안전 장면 전환은 각각 하나의 IndexedDB 트랜잭션으로 저장한다. 같은 중단 요청 ID는 장면을 중복 생성하지 않는다.

책상에는 선택형 ‘작업한 날’과 ‘자료 수’ 보기를 추가했다. 작업한 날은 카드·영역·다음 행동 변경 또는 장면 저장이 있었던 최근 30일의 날짜 수를 해당 브라우저에 집계한다. 열람·보기 위치 변경은 세지 않으며 과거 기록을 추정하지 않는다. 자료 수의 종이 층은 완료된 스캔의 파일 수만 표현한다. 부분 스캔은 ‘최소 n개 확인’으로 표시한다. 표지 원색, 카드 크기, 저장 위치는 유지하고 정확한 수치는 문자와 목록 보기에도 나타낸다. Kook 캐릭터와 기기 간 동기화는 추가하지 않았다.

검증: 작업 복사본에서 46개 자동 테스트와 프로덕션 빌드 성공. 로컬 브라우저의 별도 샘플 저장소에서 다음 행동 작성 → 중단 → 책상 복귀 → 재개 요약 → 과거 장면 이어가기 → 안전 장면 2개 표시 → 새로고침 뒤 작업 상태 복원을 확인했다. 파일 수 9개, 처음에는 ‘작업 날짜 기록 없음’, 중단 후 ‘최근 30일 작업 1일’ 표시도 확인했다. 실제 폴더 선택·브라우저 프로세스 재실행·장면 한도 200개·실제 OS 파일 변경·다중 탭은 아직 검증하지 않아 AC10~14 전체를 통과로 체크하지 않는다. V의 단계 구간과 시각 언어는 사용자 이해도 실험 전의 시안이며 개선 효과를 입증한 결과로 취급하지 않는다.

## 시작 전 알려진 확인 사항

1. 이전 `handoff/cursor-final-prompt.md`는 Tauri·4 Wall용이다. 이번에는 사용하지 않는다.
2. 현재 파일 ID는 경로·수정 시각·크기에 의존한다. 새 구현에서는 안정적인 Asset ID가 필요하다.
3. 현재 화면 상태는 useState 중심이며 새 장면·Repository 모델 구현이 필요하다.
4. 백업 가져오기의 10MiB 상한과 지원 최대 데이터 크기의 충돌 여부를 확인해야 한다. 정상 내보내기를 다시 가져올 수 있어야 한다.
5. 명시적 경로 재연결 시 이미 등록된 Asset과의 고유 경로 충돌·참조 정합성을 설계해야 한다.
6. 좁은 화면 읽기 모드와 200% 확대 접근성은 실제 화면에서 함께 검증해야 한다.

검증:
- `npx vitest run` 67개 통과(신규 6개: 단계 경계값, 기존 카드 크기 불변, 중복 자료·상자 합계·누락 제외, 부분 스캔 경고 없음(AC34), 주 1회 배너·제안값, 저장소 `budgetBytes` 저장). `npm run build` 성공.
- 내장 브라우저 샘플 저장소(17KB): 책상 카드 “17KB · 방 크기 미정” → 정리 상자 패널에서 “1GB (제안)” 선택 → “17KB / 1GB”. IndexedDB로 방 크기를 20KB로 바꾸면 “방이 거의 찼어요”와 점토색 막대, 10KB면 방을 열 때 배너(큰 파일 5개). ‘방 크기 늘리기’로 1GB 저장, 같은 주에 다시 넘겨도 배너 다시 안 뜸. 가상 상자 기록 하나로 “그중 정리 상자 16KB”가 책상·방 막대에 표시됨. 콘솔 오류 없음. 확인 뒤 샘플 기록은 상자 비움·방 크기 1GB로 되돌림.

미검증·남은 것:
- 샘플 파일이 모두 1MB 미만이라 2~5단계 아이콘·카드 크기는 화면에서 보지 못함(단위 테스트만).
- 폴더 연결 확인 창의 방 크기 고르기는 실제 폴더 선택이 필요해 브라우저에서 확인 못 함.
- 지시서 6번 “지난 확인보다 n 줄었어요”와 PRD의 방 배경 채움은 하지 않음. 폴더 새로고침(6단계)이 없어 줄어든 합계를 비교할 기회가 아직 없음.
- 넘친 방 배너는 띄운 순간 `budgetNoticeAt`을 남기므로, 바로 새로고침하면 그 주에는 다시 뜨지 않음.
- 책상 카드에 상자 줄과 경고가 함께 있으면 표지 띠가 46px에서 29px로 눌림(버튼은 카드 안에 들어옴). ‘자료 수’ 보기·부분 스캔 줄까지 겹치면 넘칠 수 있음.

## 결정 기록

아직 제품 범위나 데이터 보존 의미를 바꾸는 결정은 없다. 아래는 7단계 전에 사용자 확인이 필요한 미해결 쟁점이다.

1. 백업 가져오기 상한과 지원 최대 데이터.
   - 위치: PRD 9장 가져오기 10MiB 상한. 지원 규모는 프로젝트 12개, 프로젝트당 장면 200개, 작업면 카드 100개, 메모 2,000자.
   - 기존 규칙: 정상 내보내기는 다시 가져올 수 있어야 한다. 문서에 없는 삭제나 축약으로 한도를 맞추지 않는다.
   - 종이 계산(직렬화 실측 아님): 카드 100개의 메모가 각 2,000자일 때 장면 하나의 메모만 약 200,000바이트(한글 UTF-8이면 약 3배)다. 장면 200개면 영문 기준 약 38.1MiB, 한글 기준 약 114MiB다. JSON 구조와 파일 메타데이터는 제외한 값이다.
   - 10MiB 안에 들어가는 가득 찬 메모 장면은 영문 기준 약 52개, 한글 기준 약 17개로, 장면 200개 한도보다 작다.
   - 상태: 미해결. 구현으로 한도를 바꾸지 않았다. 7단계 시작 시 최대 크기 샘플을 실측하고, 정책 변경이 필요하면 근거와 권장안을 사용자에게 묻는다.
2. PRD 12장과 단계별 지시서의 단계 번호.
   - 12장은 1~5단계로 P0를 묶는다. 지시서는 같은 P0를 0~9단계로 나눈다.
   - 채택: 구현 순서는 지시서를 따른다. P0 범위는 줄이지 않는다. 기획서와 PRD 본문은 수정하지 않았다.
3. 명시적 경로 재연결 시 이미 등록된 Asset과의 복합 고유 인덱스 충돌은 6단계 설계 항목으로 남긴다. 이번 점검에서 병합 규칙을 확정하지 않았다.
4. 1단계 저장 구조.
   - 스키마 버전은 1이다. 스토어는 projects, roots, rootHandles, assets, workspaces, scenes, settings, events.
   - rootHandles는 PRD 6장의 스토어 목록에 없는 추가 스토어다. 핸들을 루트 메타데이터와 분리하라는 1단계 지시를 따른 것이며, 백업 포함 여부는 7단계에서 핸들 제외로 유지한다.
   - 영역 이름 80자, 표시 이름·폴더 이름 255자, 표지 색 32자는 명세에 없는 저장 상한이다. 제품 의미를 바꾸라는 결정은 아니다.
   - 같은 장면 ID는 덮어쓰지 않는다. 과거 장면 불변은 5단계에서 화면 흐름으로 다시 검증한다.
